# Codex worker session integration spike

## Status

Completed on 2026-08-16 against Codex CLI `0.148.0-alpha.9` on Windows.

## Question

Can the native PowerShell Factory launch Codex workers while preserving the
same operator experience that Claude Code provides through Agent View?

In particular, can a PowerShell process create a Codex worker that appears in
the orchestrator's `/agent` or `/subagents` picker?

## Result

Codex is a viable Factory worker runtime, but an independently launched Codex
worker cannot be inserted into another Codex conversation's subagent tree
through the current public CLI or app-server protocol.

The recommended implementation is therefore:

- keep queue mutation, scheduling, reconciliation, and integration in native
  PowerShell;
- launch each Codex worker as a persisted `codex exec --json` session;
- capture the UUID from the `thread.started` JSONL event and store it on the
  Factory task;
- make `factory status` the authoritative cross-worker view;
- make `factory chat <task-id>` open the saved worker with
  `codex resume <thread-id>`;
- expose the selected runtime through `factory start -Agent codex` and store it
  in private project runtime configuration.

These workers will be available in Codex's saved-session picker when
non-interactive sessions are included, but they will not appear as children in
the orchestrator's `/agent` picker.

## Implementation update

Implemented on 2026-08-16. `factory start -Agent codex` now persists the
private worker selection, launches Codex through `exec --json`, reconciles the
saved UUID/PID/JSONL stream, exposes runtime-aware status and doctor output,
and uses guarded archive/delete lifecycle actions. `factory chat` prints a
capture-aware resume wrapper: after the interactive Codex TUI exits, the same
thread emits a machine-readable plan/result so Factory state catches up. The
synthetic E2E uses a fake Codex executable and makes no authenticated model
call.

## Evidence

### Public CLI behavior

The installed CLI exposes the required worker primitives:

```text
codex exec --json ...
codex exec resume <session-id> <prompt>
codex resume --include-non-interactive
codex resume <session-id>
codex archive <session-id>
codex delete --force <session-id>
```

`codex exec --json` emitted a stable UUID in a `thread.started` event and
persisted the session successfully. `codex exec resume` can continue the same
worker non-interactively, while `codex resume` opens it interactively.

Official Codex documentation describes `/agent` and `/subagents` as a picker
for subagents spawned from the current session, and describes
`--include-non-interactive` as the way to include `codex exec` sessions in the
normal resume picker:

- <https://learn.chatgpt.com/docs/agent-configuration/subagents>
- <https://learn.chatgpt.com/docs/developer-commands?surface=cli>
- <https://learn.chatgpt.com/docs/codex/noninteractive>

### Protocol schema

Stable and experimental schemas generated by the installed CLI were inspected
with:

```powershell
codex app-server generate-json-schema --out <dir>
codex app-server generate-json-schema --experimental --out <dir>
```

`ThreadStartParams` has no `parentThreadId`, subagent source, or other parent
attachment parameter. `ThreadForkParams` can record `forkedFromId`, but a fork
is not a spawned subagent and does not acquire `parentThreadId`.

`parentThreadId` exists only on returned thread metadata. Its schema states
that it is set only when the thread is a subagent. `thread/list` can filter by
`parentThreadId` or `ancestorThreadId`, but those are discovery filters, not
creation controls.

The app-server itself is an experimental integration surface, and its parent
and ancestor filters are experimental. Factory does not need it for the first
Codex runtime implementation:

- <https://learn.chatgpt.com/docs/app-server>

### Controlled session comparison

Three local thread records were compared through `thread/read`:

| Kind | `source` | `parentThreadId` | Meaning |
| --- | --- | --- | --- |
| Interactive orchestrator | `vscode` | empty | Root conversation |
| Real Codex child | `subAgent` | orchestrator UUID | Visible descendant |
| PowerShell-launched worker | `exec` | empty | Independent saved session |

An additional ephemeral `thread/start` request supplied the orchestrator UUID
as an undeclared `parentThreadId` field. The server accepted the request but
ignored the field and returned another root thread with an empty
`parentThreadId`. This rules out relying on an undocumented passthrough field.

## Why the exact Agent View cannot be reproduced natively

Codex assigns the parent relationship when the parent agent invokes its
internal subagent-spawn tool. The public CLI and app-server can start, resume,
fork, list, archive, and delete root sessions, but cannot externally declare a
new session to be a child of an existing conversation.

Asking the orchestrator model to spawn every worker would produce real child
threads, but it would also put worker launch back behind an AI turn, couple
worker lifecycle to the orchestrator conversation, and weaken the native
scheduler boundary. That is contrary to the Factory architecture.

## Proposed operator experience

Start or resume the Factory with an explicit runtime:

```powershell
factory start -Agent codex
```

The persisted private project configuration supplies the default on later
starts. A command-line flag overrides it for that start. Repository defaults
remain language- and user-neutral.

Factory status should identify the runtime and expose the useful action:

```text
╭─ Factory ─ motivehr ─ agent codex
│  running ─ workers 2/10
├─ WORKERS
│  ├─ 121... ─ running ─ Codex 01a00af3...
│  │  └─ Open: factory chat 121...
│  └─ local:42 ─ review ─ Codex 01a00b11...
│     └─ Review: factory review local:42
╰─ Factory enabled
```

The task-oriented commands remain identical across Claude and Codex:

```powershell
factory status
factory inspect <task-id>
factory chat <task-id>
factory go <task-id> -Direct
factory hold <task-id>
factory reject <task-id>
```

For Codex, `factory chat` resolves the stored UUID and launches:

```powershell
codex resume <thread-id> -C <worktree>
```

The user can also browse independent workers directly with:

```powershell
codex resume --all --include-non-interactive
```

This is a different picker from `/agent`, but it preserves direct access to
every worker conversation.

## Runtime implementation boundary

The first implementation should use only stable CLI features:

1. Resolve `codex` with `Get-Command`; do not assume npm, the standalone
   installer, Codex Desktop, or a hard-coded binary path. A user-managed
   `codex.cmd` wrapper is valid.
2. Run a startup capability probe for `exec --json`, `exec resume`, and
   `resume --include-non-interactive`.
3. Launch in the task worktree and capture stdout and stderr as UTF-8 without
   merging protocol JSONL with diagnostic output.
4. Store the Codex thread UUID, process ID, runtime name, CLI version,
   worktree, and last observed event on the task.
5. Reconcile both process state and persisted session state. A missing process
   is not enough to classify a worker as failed because the Codex turn may
   already have completed successfully.
6. Resume the same UUID for follow-up, rework, and review prompts instead of
   creating a replacement session.
7. Archive a completed worker during normal cleanup. Reserve permanent Codex
   session deletion for an explicit destructive option.

No app-server dependency is required for this path.

## Performance finding

The minimal controlled `codex exec` prompt completed successfully, but the
user's full Codex configuration initialized unrelated plugins and unavailable
MCP servers. The run took about ten seconds and reported roughly 17,700 input
tokens for a trivial response.

Before enabling Codex workers broadly, the implementation should measure two
launch modes:

- normal user configuration, for maximum compatibility;
- an isolated Factory execution configuration, for predictable startup and
  token cost while retaining authentication and project `AGENTS.md` rules.

Factory must not silently disable user-required tools. The isolated mode
should be explicit in private runtime configuration and should receive an E2E
test before becoming the default.

## Installation finding

Factory must not manage or replace the user's Codex installation. The tested
machine intentionally resolves `codex` through `C:\bin\codex.cmd`, which
selects the CLI bundled with Codex Desktop because the standalone Windows
installer is not usable in that environment.

Runtime detection must therefore be capability-based, not installation-based.
`codex update` failure is informational and must not prevent Factory from using
an otherwise compatible CLI.

## Estimated implementation

The Codex worker runtime is a medium-sized change rather than a rewrite:

- **Runtime adapter and JSONL lifecycle:** medium.
- **Status, inspect, chat, cleanup, and reconciliation integration:** medium.
- **Synthetic E2E with a fake Codex executable:** medium.
- **Optional real authenticated smoke test:** small, opt-in only.
- **Exact `/agent` parent grouping:** not implementable through the current
  supported external interfaces.

The implementation should be delivered after the already accepted native
`factory new` and `factory go <id> -Direct` work, or as a separate phase with
its own task document and acceptance tests.
