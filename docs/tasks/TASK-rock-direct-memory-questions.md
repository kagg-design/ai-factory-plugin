# ROCK: вопросы к утру и принятые рабочие решения

Дата: 2026-10-23. Ветка: `codex/rock-direct-memory`.

Первая реализация находится в отдельном worktree. Рабочие runtime, задачи Asana,
сессии работников и Windows Task Scheduler не менялись. Новый режим выключен.
Прямой режим использует снимки из браузера без Asana-коннектора.

## Согласованные решения

Игорь ответил на пункты 1–4 в чате 2026-10-23: «да, со всем согласен».
Ремонт обоих дефектов тестовой оснастки разрешён отдельно в том же чате.
Повторное согласование этих решений не требуется.

1. **Пилот.** Начать с Access и одной подходящей задачи: сначала
   прямой ответ работнику, затем передача следующей задачи. Задачу выбрать по
   актуальному состоянию в браузере и проверить её ограничения перед запуском.
   Billing на первом этапе может остаться наблюдателем.
2. **Что показывать в Asana.** Рекомендую оставлять состояние задач, итог
   проверки и вопросы людям; переписку агентов и технические подтверждения хранить
   локально. Содержательный итог на эпике нужен для читаемого журнала, в соответствии
   с последующим уточнением из канала #ai; технические подтверждения там не нужны.
3. **Работа с браузером.** Основной Codex-оркестратор фабрики должен читать
   Asana через браузер и обновлять видимое состояние доски. Используется Codex с
   доступным браузером; перед автономным запуском нужно проверить его инструменты.
   В прямом ROCK-процессе коннекторов и нового пути чтения через API/токен нет.
4. **Управление и история.** Используются для нового режима команды
   `factory rock pause/resume`, а старые решения из Asana сохранить и импортировать
   как снимки. Старые `/pause` в Asana останутся историческими записями.
5. **Отдельные дефекты тестов.** Ремонт разрешён и выполнен в этой ветке:
   ledger-фикстура получает пакет зависимостей; запуск Codex проверяется по живым
   процессам и закрытию каналов, с отрицательным контролем наследования handles.

## Уточнения из переписки #ai

Переписка предоставлена Игорем прямо в чате; Slack не читался и сообщений туда нет.
Она описывает существующий рабочий процесс, который нужно сохранить при миграции:

- Один ROCK-оркестратор ведёт оба рока, планирует, исследует, отвечает фабрикам и
  проверяет результат; код пишут фабрики. Codex следит за исправностью конвейера.
- Общая задача имеет одного владельца. Другой рок наблюдает и ждёт. Зависимости
  между двумя репозиториями должны блокировать преждевременный запуск.
- Дорогой модельный цикл запускается после дешёвой проверки изменений. Проверка
  результата после merge может породить отдельную задачу на обнаруженный дефект.
- Изменения живого поведения требуют одобрения Игоря до merge. Доступы, секреты,
  необратимые действия в production и выход за согласованные решения — к человеку.
- Читаемость журнала, возможность восстановить цепочку решений и вмешаться с
  телефона сохраняются. Перенос технического обмена из Asana не отменяет этого.
- Планировщик применим и к другим командам: действия исполнителя должны оставаться
  отдельным адаптером, а не требовать Git/worktree для любого вида работы.

Первый прототип ещё не полностью реализует этот контракт. В частности, отдельные
mutex/контексты ROCK нужно объединить в координацию двух целей; требуется явный
контракт cross-repository prerequisites и проекция важных событий в Asana через
браузер. Это условия дальнейшего включения, а не новые вопросы к Игорю.

## Решения, принятые для самостоятельной работы

- Постоянный ID ROCK — GID эпика; переименование и несколько репозиториев его
  не меняют. Память находится вне Git, по умолчанию в LocalAppData/ClaudeFactory/rocks.
- Владельцы и наблюдатели задаются явными привязками, а не текстом ответа модели.
- Модель только читает и предлагает типизированные действия; исполняет их
  проверяемый код фабрики. Нет действий GO, merge, произвольных команд и
  предоставления новых доступов.
- Решения человека и агентов различаются. Повторная доставка не дублирует
  постановку задачи или ответ. Сохранённый результат переживает прерывание.
- Пауза, неактивность и ручной hold не отменяются агентом. Незавершённый обмен
  учитывается перед уходом уже активной фабрики в простой.
- Исполнение учитывается локально. Asana остаётся источником требований и
  интерфейсом для людей. Снимки из браузера импортируются без изменения текста.
- Первая версия принимает новые задачи с уже известными Asana ID и проверенными
  владельцами. Создание новых карточек и обновление доски через браузер — следующий
  этап после проверки выбранного основного оркестратора.

## Ограничения проверки

Проверки выполняются на временных репозиториях с подставными службами и ответами
модели. Живой ROCK и реальные операции с Asana не запускались. Сценарий с реальной
моделью и браузером предстоит проверить на пилоте.
